§3.1 produce `r1 == 0 && r2 == 0` (DESIGN §8).

Esta fase es sobre todo lectura y escritura, no código. Lo que se entrega es un texto
propio, en `F1-explicacion.md`. El código de apoyo va en `src/main/java/wsp/f1/` y sus

no es el proyecto.

## Lo que debe dejar cada ejercicio

1. **Reproducción.** Cuántas veces sale `0,0` en esta máquina, y con qué JVM. Si no sale, se
   anota igual (ya pasó con `Publicacion` en la F0). Probar también con `-Xint`.
2. **`volatile`.** Por qué la escritura seguida de lectura deja de poder reordenarse.
3. **Reglas de `happens-before`.** Una lista propia, no copiada, con la fuente de cada una.
4. **Atomicidad / visibilidad / orden.** Tres fallos distintos, tres causas distintas.
5. **Store buffer.** Un diagrama con los dos núcleos, sus buffers y la memoria.
6. **Modos de acceso.** Una tabla de qué garantiza cada modo y cuál necesitará el deque.
7. **Explicación.** Se puede leer sin ver el código y responde: ¿por qué, aunque el código
   "parece imposible", ocurre?

## Resultados medidos (ejercicios 1 y 2)

Java 23, 8 hilos de hardware, dos hilos con barrera de espera activa por iteración.
`java -cp target/classes wsp.f1.CerosMutuos 2000000 3` tras `mvn compile`.

| Variante | (0,0) en 2.000.000 | Notas |
|---|---|---|
| NORMAL | 14.953 / 9.545 / 8.888 (~0,5 %) | Ocurre, y cambia de corrida en corrida |
| NORMAL con `-Xint` | 523 y 240 de 300.000 (~0,1 %) | También sin JIT: con intérprete puro sigue saliendo, así que la causa es el procesador, no solo el compilador |
| VOLATILE | 0 / 0 / 0 (y 0 con `-Xint`) | Prohibido por el JMM; por eso el test sí lo afirma |

Contraste con `Publicacion` de la F0: allí la carrera no se vio; aquí sí, porque el patrón
(escritura seguida de lectura de *otra* variable) es justo el que el store buffer reordena.
